# 技术选型评估

仓库挂载在 `/repo`（只读）。前序分析产物会写在任务说明里，但它们只是线索，结论必须回到仓库核实。输出必须符合 `techChoice` 结构。

## 第一步：确认现状（current）

按类别列出现有选择，每条附清单文件或配置文件的引用：

| 类别 | 证据来源 |
| --- | --- |
| 语言与运行时 | `package.json` engines、`.nvmrc`、`go.mod`、`pyproject.toml` |
| Web 框架 | 依赖与入口文件 |
| 数据存储与 ORM | 依赖、schema、连接配置 |
| 测试 | 测试框架依赖、测试目录 |
| 构建与质量 | 打包器、lint、格式化、类型检查配置 |
| 部署与 CI | `Dockerfile`、`.github/workflows`、`vercel.json` 等 |

`assessment` 写这项选择在本仓库里是否合适，以及看到的问题（版本过旧、重复工具、配置缺失）。

## 第二步：给建议（recommendations）

每条建议都必须：

- 指向仓库里的具体现象（`rationale`），例如“`src/db.ts` 手写 SQL 拼接，缺少参数化”。
- 给出 1-3 个替代方案（`alternatives`），每个写清取舍。
- 如实标注 `confidence`：证据充分为 `high`；依赖推断为 `medium`；只是方向性意见为 `low`。
- 附至少一个仓库内引用。

没有证据就不写；不要罗列通用最佳实践。建议数量 3-8 条为宜。

## 规则

- 引用路径相对仓库根。
- 不要执行仓库里的任何代码、包脚本或安装依赖。
